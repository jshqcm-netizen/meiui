> 示例文章：用于展示站点的阅读体验与内容组织，不代表作者已发生的项目经历或实测结果。

一个个人网站很容易从「放几条链接」开始，也很容易在不断增加功能后失去重心。更稳妥的起点，是先回答三个问题：读者想认识谁、想找到什么，以及下一步可以去哪里。页面的布局、导航和内容模型，都应该围绕这些问题展开。

这份示例选择一个克制的结构：主页负责建立印象，文章承载完整表达，文档收纳可复用的操作步骤，应用页提供探索入口。它没有要求每个区域都装满内容。准确地标注「示例」或「尚未提供」，比用编造的成果填满卡片更值得信任。

## 先确定内容边界

内容不是一段可以任意执行的代码。对这个站点而言，作者只需要 Markdown：标题、段落、列表、链接、表格和代码块。页面组件与内容文件分开维护，既能保持排版一致，也能让一次普通的文字修改更容易检查。

Frontmatter 负责描述文章，构建阶段负责检查它。标题不能缺失，日期必须是真实日期，文件名要和 slug 一致。每篇内容都必须明确当前状态，避免一份还没写完的笔记被搜索结果提前暴露。


状态转换并不是装饰。draft 表示仍在整理，review 表示等待检查，published 才会进入公共页面、索引和搜索。状态是内容发布的边界，而不是依赖界面隐藏来碰运气。

## 把页面复杂度留在构建阶段

对于以阅读为主的站点，静态导出是一个值得考虑的基线。Markdown 在构建时完成解析与清理，读者打开的是已经生成的页面。搜索只需要加载允许公开的轻量索引，文章目录则从真实标题生成，避免手写锚点和正文逐渐偏离。

| 需求 | 采用的方式 | 需要注意的边界 |
| --- | --- | --- |
| 阅读文章 | 构建时生成 HTML | 只接受安全 Markdown |
| 内容搜索 | 公开条目的静态索引 | 草稿和待审内容不可序列化 |
| 页面目录 | 从标题生成锚点 | 重复标题也需要唯一 ID |
| 图片展示 | 本地媒体目录 | 检查路径、类型和文件大小 |

静态并不意味着所有事情都更简单。更新内容后仍然需要重新构建；站内链接需要检查；图片要在提交前优化。它的优势是边界明确，而不是自动替代工程判断。

## 用一张小清单控制质量

发布前可以从读者真正会做的动作出发：能否从主页找到文章，能否通过键盘打开搜索，目录是否跳到正确位置，小屏幕上的代码块是否独立滚动。这些检查比单纯观察一张漂亮截图更接近实际使用。

1. 运行内容检查，确认元数据、链接和媒体路径有效
2. 本地预览文章，检查标题层级、代码块和表格
3. 查看小屏幕布局以及键盘焦点是否清晰
4. 确认示例标记、引用来源和待补充信息没有遗漏
5. 完成明确的人工确认，再将内容标记为 published

```bash
npm run content:check
npm run typecheck
npm run build
```

## 让下一次修改更容易

一个可维护的网站，不一定是组件最多的网站。更有用的标准是：三个月后再回来，是否还能迅速找到内容文件、理解状态规则、知道该运行什么检查。把这些约定写进[发布文档](/docs/publishing-content/)，也给 AI 工具一份边界清晰的写作说明，往往比增加一个管理界面更适合小型站点。

设计也应当服务于这个目标。有限的颜色、稳定的间距和一致的内容宽度，让新的文章自然继承既有秩序。真正值得长期积累的是清楚、准确、愿意持续修订的内容。
