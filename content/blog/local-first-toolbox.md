> 示例文章：以下是设计方法与伪代码，不是已经上线的产品介绍，也不包含实测性能承诺。

文本整理、格式转换和清单编辑，常常不需要复杂的服务端。对于这类小工具，可以先问一句：核心操作能否只在浏览器完成？如果答案是肯定的，一个本地优先原型就能让数据流更容易理解。

## 先写清楚数据流

把流程拆成输入、处理和输出。用户粘贴一段文本，浏览器中的纯函数处理它，结果可以复制或下载。没有网络请求，就不应该在界面上出现模糊的「正在同步」；没有云端备份，也不能暗示换设备后数据仍然存在。

```ts
function normalizeLines(input: string): string {
  return input
    .split(/\r?\n/)
    .map((line) => line.trim())
    .filter(Boolean)
    .join('\n');
}
```

这段示例只展示文本转换，不涉及保存或传输。真实工具仍然需要考虑大输入、空输入、撤销操作和失败提示。

## 保存应该是可以理解的选择

浏览器存储并不等于永久备份。清理站点数据、使用隐私窗口或更换设备，都可能让本地内容消失。如果需要保存，界面应明确告知保存位置，并提供可检查的导出格式。

| 能力 | 最小实现 | 对用户的说明 |
| --- | --- | --- |
| 临时处理 | 页面内存 | 刷新后可能消失 |
| 本机保留 | 浏览器本地存储 | 仅在当前设备和浏览器可用 |
| 手动备份 | 下载 JSON 或文本 | 由用户决定保存位置 |

## 在增加连接前，先证明需要连接

账户、分析脚本和外部 API 都会改变工具的隐私边界。若确实需要接入，应说明哪些数据会离开设备、发送给谁、用于什么目的，并根据需求获得批准。本地优先是一种默认方向，不是一句可以替代验证的隐私承诺。

对于第一版原型，清楚的错误提示、可用的键盘操作和一份可靠的导出文件，通常已经能回答很多问题。更多功能可以留到真实需求出现之后。
